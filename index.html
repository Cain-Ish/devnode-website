02 — DECISIONS, WITH THE REASONING ATTACHED

Calls I've actually had to make

Recoil and React Query in the same app — why not just one?

DELIBERATE, NOT ACCIDENTAL

Server state and client state have different lifecycles and pretending otherwise is how you end up hand-rolling cache invalidation. React Query owns anything the API is the source of truth for; Recoil owns genuinely local UI state. The rule that matters is that no piece of state lives in both — that is the bug factory, not the two libraries.

Why hold a 250 KB gzipped budget when nobody asked for one?

CI FAILS THE BUILD

A budget nobody enforces is a wish. Put it in CI and it becomes a design constraint: someone has to justify the 40 KB date library in review, which is exactly the conversation you want happening then rather than in a performance audit eighteen months later. It also kills the ratchet effect, where every sprint adds two kilobytes and nobody is ever responsible.

JSON Schema-driven forms, or hand-written ones?

SCHEMA — UP TO A POINT

When a Python backend already owns the validation rules, duplicating them in TypeScript means they will drift, and the drift surfaces as a user submitting something the server rejects for reasons the UI never mentioned. Generate from schema. The honest caveat: bespoke interaction design fights the generator, so I keep an explicit escape route for the two or three forms that genuinely need it instead of bending the abstraction until it screams.

Accessibility — audit at the end, or as you go?

AS YOU GO, AND NOT BY PLUGIN

Automated tooling catches perhaps a third of real problems, and never the ones that matter most: focus order that makes no sense, a modal you cannot escape, a live region that shouts over itself. I build with the keyboard and a screen reader in the loop, because retrofitting semantics into a finished component tree costs several times what writing it correctly did.

Incremental migration or a clean rewrite?

INCREMENTAL, ALMOST ALWAYS

Rewrites ask a business to stop delivering value for a quarter or more on the promise that the second attempt will be wiser. Sometimes that is genuinely right. Usually it means re-learning every hard-won edge case the old code encoded, and the new version ships with a fresh set of bugs plus none of the institutional memory. I would rather move a codebase in reviewable steps that each ship.

An in-repo agent layer — skills, hooks and CLAUDE.md docs committed alongside the code — carrying lint rules, folder structure, naming and review standards, so output arrives shaped like the codebase instead of like a tutorial. Hooks matter more than prompts: they enforce what the model drifts away from by the third file.

An MCP server I actually shipped

A component-catalogue MCP server that exposes a design system to agents, so generated UI reaches for the real library instead of inventing a fourth button. The agent queries the repo and dependency graph at run time rather than reasoning about a paste that went stale two commits ago — most “the AI wrote nonsense” stories are context failures wearing a model costume.

Subagents with narrow scopes

One agent per concern with explicit handoffs — migrate, then test, then review — because a single prompt attempting all three fails silently at the middle one. Narrow scopes also mean a failure traces to a step you can fix.

Evals, or it is vibes

Agent output gets checked against expected outcomes the way any other code path would be. Without that you cannot tell an improvement from a regression, and “it felt better this week” is not something I am willing to put my name on.

If your team's honest position is “we tried Copilot and it wrote nonsense” — that's a reasonable prior. The difference is almost always context and constraints, not the model. Happy to be specific about it.

06 — THE PART MOST PORTFOLIOS SKIP

Two things I got wrong, in my own commit messages

A test suite on a project template of mine started dying on memory. I raised the per-worker heap to 4 GB and wrote a commit message explaining, with some confidence, that the import graph simply needed more room. Writing the wrong diagnosis down as if it were settled is the part I'd flag in someone else's review.

An hour later I found the actual cause: a mock in one test returned a fresh object literal on every render, which broke the stable-reference contract the data layer depends on, so it re-fired its reset on every render — roughly 19 MB a second until the worker died at 4.5 GB. Hoisting the mock to a module-level constant took that test's peak from 4,543 MB to 365 MB. I reverted my own heap bump in the same commit and called it what it was: a band-aid over a leak. The rule I took from it is that a resource ceiling is almost never the fix — if something needs more memory than it should, the number is the symptom, and I don't touch the limit now until I can name the allocation.

The costlier one was further outside my lane. I had scaffolded a service at two replicas over a single-writer datastore, then “hardened” it by adding a pod disruption budget and writing a paragraph justifying the topology. Five days later I deleted both and called the design architecturally impossible in my own commit message: a single-writer store dictates the deployment topology, and I had reasoned from the deployment inward instead. Caught in review rather than production, and cheap to undo — but it is exactly why the list above separates what I own from what I merely work alongside.
